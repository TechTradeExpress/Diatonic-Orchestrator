# ADR-0015: Explicit offline capability demand and supplied driver support

## Contract, internal policy and deferred behavior

Resource Model v0.1 §§10–12 distinguishes lifecycle ownership, capabilities,
Provider instances and drivers. Managed phases require compatible provider
resolution when required, while external/disabled phases must not become managed
actions. Omitted ownership has no default. The contract gives capability examples,
not an exhaustive automatically derived vocabulary or a driver discovery scheme.

Issue #32 authorizes M2.7's internal interpretation of those examples and ADR-0009
§§3/5: require an explicit resource/phase analysis request and inspect only supplied
offline driver facts. The seven mappings below are the initial internal vocabulary,
subject to independent PR review. No normative Resource Model document or versioned
namespace is modified. ProviderBinding evaluation/selection, compatibility with an
environment and execution remain deferred to separate increments.

## Explicit request API and ownership

```python
from diatonic.compiler.capabilities import PhaseRequest, analyze_phase_request

analysis = analyze_phase_request(index, PhaseRequest("VirtualMachine/app01", "provision"))
analysis.fact.ownership           # "managed" if explicitly declared managed
analysis.fact.required_capability # "virtual_machine.provision" in that case
```

`PhaseRequest` is a frozen/slotted record with a strict canonical ResourceReference
and exactly `observe`, `provision` or `configure`. Identity/name case is preserved.
No query is generated by loading YAML, declaring ownership, desired state,
prevent_destroy, Stage assignment or dependencies. The API requires the request
argument and never scans other resources/phases for demand.

`PhaseAnalysis` separates a portable frozen/slotted `fact: PhaseFact` from detached
`source: PhaseSource`. The fact contains the immutable request, ownership outcome,
`ownership_origin` and optional required capability:

| Requested ownership | Outcome | Capability demand |
| --- | --- | --- |
| managed | `managed` | Explicit mapped capability, or unsupported-pair error |
| external | `external` (externally owned) | None |
| disabled | `disabled` (not applicable) | None |
| omitted/null | `unspecified` | None |

For example, VM phases `{observe: external, provision: managed, configure: disabled}`
yield external/no demand, managed/virtual_machine.provision and disabled/no demand
for those three **separately requested** phases. A VM without lifecycle yields
unspecified/no demand. No Provider, Binding or driver descriptor is needed to
identify the managed capability. There is no selected-provider field or operation.

`ownership_origin` preserves declaration details using Pydantic's existing field
presence information: `lifecycle_omitted`, `lifecycle_null`, `phases_omitted`,
`phases_null`, `phase_omitted`, `phase_null`, or `declared`. Every omitted/null case
has ownership unspecified, without collapsing its original declaration shape or
inventing managed/external/disabled ownership. These origin labels are internal
facts, not new YAML fields. Normalized IR omission/null behavior is untouched.

## Initial capability vocabulary

The read-only `CAPABILITY_VOCABULARY` is an explicit table of §11 examples for
currently supported resource kinds, ordered lexicographically by kind/phase keys:

| Resource kind | Phase | Required managed capability |
| --- | --- | --- |
| VirtualMachine | observe | virtual_machine.observe |
| VirtualMachine | provision | virtual_machine.provision |
| VirtualMachine | configure | virtual_machine.configure |
| Network | observe | network.observe |
| Network | provision | network.provision |
| Hypervisor | observe | hypervisor.observe |
| Hypervisor | configure | hypervisor.configure |

Network configure, Hypervisor provision and all Image/Stage/Provider/ProviderBinding
phases lack an initial mapping. A **managed** request for one of them raises
`unsupported_managed_phase`; no identifier is invented by case conversion or string
concatenation. External/disabled/unspecified ownership still returns its outcome for
those pairs. NetworkDevice examples are excluded because that kind is unimplemented.
Expansion of this internal table needs its own review and tests.

## Independent driver support metadata

```python
from diatonic.compiler.capabilities import (
    DriverSupportDescriptor, DriverSupportMetadata, assess_driver_support,
)

metadata = DriverSupportMetadata((
    DriverSupportDescriptor("example.driver", ("virtual_machine.provision",)),
))
assess_driver_support(metadata, "example.driver", "virtual_machine.provision").status
# "declared_supported"
assess_driver_support(metadata, "example.driver", "virtual_machine.configure").status
# "declared_unsupported"
assess_driver_support(metadata, "other.driver", "virtual_machine.provision").status
# "metadata_unavailable"
```

These are frozen/slotted **in-memory facts**, not YAML resources, Provider instances,
installed drivers, functions or live connections. Driver and capability identifiers
reuse strict ResourceName syntax (nonempty, no slash/whitespace, no scalar coercion).
Capability IDs remain opaque and are not limited to the initial phase vocabulary:
a supplied declaration does not extend that table or establish a phase mapping.
IDs are case-sensitive and never interpolated or inferred from a Provider's driver,
a Binding's capability, extensions, an installed package or environmental data.

Descriptor capability collections and metadata descriptor collections must be
explicit lists or tuples. Both are required constructor arguments; there is no
implicit empty-capability declaration. Empty collections are allowed when supplied.
Other collection types, strings, maps and arbitrary objects are rejected. Constructors
own/canonicalize data: capabilities sort lexicographically, descriptors sort by driver
ID, and metadata copies validated descriptor facts. Duplicate capability entries and
driver IDs fail, choosing the smallest duplicate identifier in canonical ordering.
Invalid element/type checks fail before duplicate checks, in supplied element order.

A supplied descriptor lacking a capability is **declared unsupported**, including
an explicitly empty capability tuple. An absent descriptor is **metadata unavailable**,
not unsupported. A supplied capability is only **declared supported**, not proof of
installation, authentication, platform/environment compatibility or readiness.
`DriverSupportAssessment` contains only queried IDs and one of these three statuses.
No fallback, selection, driver import, discovery or execution occurs.

`analyze_phase_request` takes no metadata argument and never calls support inspection.
Support inspection takes no resource index, Provider or Binding and never creates
phase demand. External/disabled/unspecified queries therefore require no support
metadata. This separation is deliberate, not a partial provider resolver.

## Input checks, diagnostics and provenance

Phase analysis consumes an existing successful, unmodified ResourceIndex. Focused
guards check the requested indexed entry's type/identity, root provenance and relevant
lifecycle/phase types, values and presence flags. It does not reparse YAML, re-resolve
references, examine other phases/resources, revalidate Provider config, or modify
schemas. Valid same-type edits before analysis have no historical snapshot to compare
against; callers must resolve again after edits. Completed facts remain detached.

`PhaseAnalysisError.diagnostic` is frozen/slotted with stable codes:

- `invalid_phase_request`: invalid canonical identity, phase or request object.
- `unknown_phase_resource`: no exact indexed identity, including wrong name/kind case.
- `unsupported_managed_phase`: managed ownership lacks a documented mapping.
- `invalid_phase_input`: obviously inconsistent requested index/model/provenance data.

Diagnostics include available identity, phase, context field path and detached source.
Constructor request errors happen before an index is available and have no source;
unknown resources also have no fabricated source. Resource-related errors preserve
available path, document number and document-root line/column. Ownership paths are
semantic field paths; root coordinates never claim an exact field's position.

`DriverSupportError.diagnostic` uses `invalid_driver_descriptor`,
`duplicate_driver_descriptor`, `duplicate_driver_capability` or `invalid_support_query`,
with duplicate IDs/capabilities when relevant and actionable messages. Driver facts
have no YAML provenance to invent. Missing Python arguments use conventional TypeError;
invalid supplied values/objects use the structured errors. No broad exception catch
hides programming errors, and no Provider config or secret values enter diagnostics.

## Immutability, determinism and later consumers

All returned/request/descriptor/diagnostic records are frozen/slotted; retained
sequences are owned tuples, vocabulary mappings are owned/read-only, and no mutable
Pydantic model, caller list or Provider config is retained. Identifiers and meaningful
ownership declarations are preserved. Equivalent configurations relocated/reordered
compare equal by `PhaseAnalysis.fact`; full equality includes actual root provenance.
Descriptor facts and assessments are independent of input ordering and file layout.

M2.8 may combine an explicit managed demand with separately validated Binding
summaries and supplied support facts. It must still review matching, priority direction,
ambiguity, compatibility requirements and unavailable metadata handling. M2.9 may
expose explicitly requested analysis in explain. Neither integration happens here.
The existing validate/graph CLI, Binding summaries, dependency facts/edges, Stage
ordering and IR serialization are unchanged and do not invoke this layer implicitly.

Runtime operation classification, phase scheduling, real/mock execution, providers'
installation/discovery/import, credential/secret lookup, state/journals, plan/apply
and destruction remain outside M2.7. This is offline library analysis only.
